# 推荐发现、漏选复盘与持仓卖出决策总规划

> **文档状态：当前业务施工入口。** 截至 2026-08-10，第一大批“推荐提醒止噪 + 统一持仓卖出风险评估”已实现并合入 `f7a3bb1`；第二大批“全市场日更发现 + 近 5 日候选记忆”尚未开发，第三、第四大批继续待开发。代码已实现不等于线上已验收，线上状态看 `ROADMAP.md` §5。
>
> 版本：1.0
> 制定日期：2026-08-10（Asia/Shanghai）
> 定位：把“自动发现值得研究的股票、解释为什么漏选、判断已持仓是否需要卖出复核”串成一条面向散户的业务闭环。
> 关联规划：推荐测量与模型验证见 `RECOMMENDATION_ACCURACY_PLAN.md`，既有散户账本与卖出提醒见 `RETAIL_EXPERIENCE_PLAN.md`，Top50 产品对标见 `QUANTVISTA_TOP50_OPTIMIZATION_PLAN.md`。
> 本文不构成投资建议；系统只提供研究与风险复核，不自动交易。

## 0. 结论与优先级

本次六个问题不是六个孤立功能，而是两条相互衔接的主线：

```text
全市场日更发现
  -> 近 5 个交易日候选记忆
  -> 当前数据复核与用户偏好过滤
  -> 量化多通道入围
  -> AI 精选/否决
  -> 推荐研究跟踪
  -> 次日漏选与误选复盘
  -> 召回、排序和 AI 增量评估

真实持仓
  -> 盘中价格/计划风险快速判断
  -> 盘后趋势、波动、资金与事件复核
  -> 统一风险等级与行动状态
  -> 中高风险才进入 AI 卖出复核
  -> 去重提醒、用户处理、后续效果复盘
```

优先级按用户价值排序：

1. **P0：停止给未持有的推荐股自动创建止盈止损提醒，统一真实持仓卖出风险。** 这是当前最直接的噪音和使用体感问题。
2. **P1：建立全市场日更发现池和近 5 日候选记忆。** 先扩大并稳定候选召回，再谈推荐排序是否更准。
3. **P1：建立“今日强势股昨日为何漏掉”与“昨日推荐今日为何失败”的成对复盘。** 只看漏掉的赢家会把系统调成追涨，必须同时看误选。
4. **P2：用既有 Quant Top-N、AI、score-blind 配对结果决定 AI 的位置，再调整排序。** 没有成熟样本前不凭感觉改权重，不直接上复杂模型。

### 0.1 是否能由一个会话全部完成

不能安全地一次完成。完整改造预计会跨越：

- 后端模型、启动迁移、推荐、选股、全市场同步、定时任务、提醒、守护、卖出复核、持仓 AI、Todo、控制器与路由；
- 前端设置、持仓、今日待办、推荐、管理评估页与 API 类型；
- 多组纯函数、数据库、幂等、用户隔离、时间点一致性和响应式测试；
- 约 **35~55 个文件**，并且候选池和卖出链路各自都有较高回归风险。

因此拆成 **3 个尽量大的可独立交付批次 + 1 个受样本门槛约束的后续批次**。每批都必须能单独上线、回滚和验收，不留下半套并行引擎。

## 1. 当前基础与真正缺口

### 1.1 已有能力，必须复用

- 推荐已经是“多源建池 -> 本地量化评分 -> Top10 交给 LLM -> 可选复核/反方 -> 信任层”，LLM 不负责搜索全市场。
- `recommendation_candidate_events` 已记录 `filtered/pool_full/scored/llm_list/picked`，并有影子标签、Recall@K、来源消融和错失收益。
- `stock_universe_dailies`、`factor_snapshot_dailies`、全市场日线与 63 因子宽表已提供日更全市场事实。
- 推荐已有 `cr1/cr2` 排名事实、`so1` fixed-hold 结果、Quant Top-N/AI/challenger/score-blind 配对评估。
- 持仓已有真实分批账本、计划止盈止损、成本收益/回撤提醒、持仓峰值、`GuardEvent`、`SellReview`、Today 收件箱和按需 `hold|trim|exit` AI 建议。
- 新闻已有 7 日窗口、来源、时间、情绪、相关标的和时点过滤，可复用精简标题，不应重新造新闻链路。
- 新表统一加入 `model.AllModels()`，生产随容器启动执行 GORM `AutoMigrate`；不要求用户手工执行 SQL。

### 1.2 当前缺口

| 问题 | 当前事实 | 缺口 |
|---|---|---|
| 推荐卖点提醒噪音 | 收盘日报会为每条推荐自动创建普通 `price` 止盈/止损规则，不验证用户是否买入 | 未持有研究对象进入主动提醒，和持仓风险混为一谈 |
| 卖出判断分散 | Alert、Guard、SellReview、PositionAdvice 各自有事实 | 没有一个“这笔持仓现在风险几级、为何升级、下一步做什么”的统一状态 |
| 候选池只在生成时存在 | 推荐请求发生时才从榜单/策略信号临时建池 | 没有每天稳定积累的全市场发现结果，无法观察信号持续性 |
| 历史候选未参与择时 | 因子覆盖 5/20/60 日走势，但候选身份没有跨日记忆 | 不知道首次入池、连续出现、排名变化、来源变化，也无法识别“连续增强后刚到买点” |
| 漏选复盘偏后验 | Recall@K 已能算阶段漏斗，但偏管理员评估、持有期为 5/10/20 日 | 缺面向每日业务的 T+1 漏选/误选清单和昨日时点解释 |
| AI 增量尚未被证明 | 已有 score-blind 与 Quant/AI 配对基础 | 不应扩大 AI 权力或重写评分，需先积累并读取配对证据 |

## 2. 不可破坏的业务边界

1. **推荐是研究对象，不等于用户已买入。** 未建立实际 `Position` 血缘的推荐，不创建主动卖出提醒；其后续表现只留在推荐追踪页。
2. **卖出决策只面向真实 `holding` 持仓。** 平仓、删除或不属于本人的持仓不得继续产生新状态或通知。
3. **系统永不自动下单。** `normal/watch/review/urgent` 是风险复核等级，不是券商交易指令；AI 输出也是研究建议。
4. **数据不可用不等于风险正常。** 没有 fresh 行情时必须为 `unknown`；技术样本或旁路事实不完整时必须显式 `partial`，不得写成“无风险”或默认 `hold`。但 fresh 行情已经触发的用户计划止损等独立硬事实不能被其他缺口吞掉，仍保留风险等级，缺失证据不参与共振。
5. **高频层零 LLM。** 盘中只做本地确定性判断；AI 仅在程序已判定 `review/urgent` 后按需运行，第一批默认由用户触发，避免每两分钟烧 token。
6. **全市场扫描全局只跑一次。** 日更发现是系统级共享事实，用户偏好在消费时过滤；严禁每个用户各扫 5500 只股票。
7. **历史复盘严格 point-in-time。** 解释昨日为何漏选只能读取昨日收盘前可知的快照、事件和新闻；今日涨幅只作为结果标签，不得倒灌昨日输入。
8. **赢家与输家成对复盘。** 每日既看“今日强势但昨日漏掉”，也看“昨日入选但今日明显落后”，防止因只学习赢家而系统性追高。
9. **不伪造市场范围。** 当前只支持 A 股 `cn`；设置页可以明确“全 A 股自动发现”，但不出现尚无数据源支持的港美股开关。
10. **未有证据不调权。** 新来源、新门控和新排名先记录事实/影子结果，满足样本门槛后才改变生产推荐。

## 3. 目标架构

### 3.1 全市场发现与推荐

```text
16:10 全市场日线同步成功
  -> 因子宽表重建 + FactorSnapshotDaily 首写不可变
  -> 全局 CandidateDiscoveryRun（幂等、可补跑）
  -> 每个内置发现通道保存 Top-N CandidateDiscoveryItem
  -> 当前日 + 最近 5 个有效交易日候选身份汇总
  -> 用当前行情/因子重新过硬门，不拿旧分直接推荐
  -> 用户 RecFilters/黑名单/风险周期过滤
  -> 多通道名额进入 LLM 名单
  -> LLM 看当前事实 + 候选时序摘要 + 有界新闻摘要
  -> RecommendationCandidateEvent 继续记录完整去向
```

发现通道至少覆盖已有策略能够真实表达的方向：趋势/突破、强势回踩、量能活跃、低位价值/质量。通道之间保留独立排名和名额，不能再用一个总分把不同票型全部挤掉。

### 3.2 统一卖出决策

```text
真实 holding 持仓
  -> 快速信号：计划止损/止盈、成本损益、峰值回撤、最新价有效性
  -> 结构信号：MA20/MA60、ATR 波动止损线、趋势转弱、量价异常
  -> 事件信号：业绩预告、解禁、龙虎榜净卖、除权、已有 SellReview
  -> 纯程序聚合为 normal/watch/review/urgent/unknown
  -> 仅等级升级或新主因时落事实与通知
  -> review/urgent 可一键请求该笔 AI hold|trim|exit 复核
  -> Today 与持仓页消费同一最新状态
```

`AlertEvent` 继续表示用户显式规则命中，`GuardEvent` 继续做推送去重台账，`SellReview` 继续保存单个利空事件；新增的聚合事实只负责把这些来源加上技术/波动信号，形成单笔持仓的统一状态，不复制或删除原始事实。

## 4. 数据设计

### 4.1 第一批：`position_exit_assessments`

建议新增追加式 `PositionExitAssessment`，一行代表“某笔持仓在某时点的一次有效风险评估”。至少固化：

- 身份：`user_id/position_id/symbol/market/trade_date/evaluated_at/session`；
- 结论：`level=normal|watch|review|urgent|unknown`、`action=hold_observe|review_trim|review_exit|unavailable`、`primary_signal`；
- 证据：版本化 `signals_json`、引用的 `alert_event_ids/sell_review_ids`、计划价、成本、现价、盈亏、峰值回撤、MA/ATR/趋势值；
- 时点：`quote_as_of/bars_as_of/data_status=ready|partial|unknown`，任何 stale/缺失项显式记录；
- 版本：`assessment_version`、参数快照/哈希；
- 通知：是否为等级升级、是否需进入 Todo。通知是否送达仍由既有通道事实负责，不在本表冒充；
- 可选 AI 关联：只保存已有 `llm_task/job_run` 引用和最终合法枚举，不复制 prompt 或完整响应。

约束：

- 相同持仓、相同交易日、相同评估槽位和相同事实哈希幂等；只在等级变化、主因变化、关键阈值首次穿越或盘后收盘快照时追加。普通价格波动只参与内存计算，不因每次报价变化刷数据库。
- 新评估先确认持仓仍为本人且 `holding`；扫描快照与落库之间已平仓时必须拒绝写入。
- 最新状态通过确定性排序查询，不在 `positions` 上再维护一份容易漂移的风险等级。
- 只有 `review/urgent` 首次出现、等级升级或主因变化时形成卖出待办；`watch/normal` 只供持仓页展示，`unknown` 进入数据缺口状态而不是卖出待办，三者均不主动推送。

### 4.2 第二批：`candidate_discovery_runs/items`

`CandidateDiscoveryRun` 固化全局一次日更扫描：

- `market/trade_date/as_of/status/universe_count/scanned_count/eligible_count`；
- `factor_version/discovery_version/source_versions/content_hash`；
- `success/partial/failed` 与安全错误摘要，启动补跑幂等。

`CandidateDiscoveryItem` 固化每个通道的短名单：

- `run_id/profile/symbol/market/rank/score`；
- 触发信号、关键因子摘要、行业、流动性、数据质量；
- `ref_price/ref_date` 与不可变 `facts_json`；
- 唯一键至少覆盖 `run_id/profile/symbol`。

规模控制：保存各通道 Top100~Top200，而不是“5500 股票 × 所有策略 × 每日”全复制。全市场底层事实已在 Universe/FactorSnapshot/DailyBar，发现表只保存“为何成为候选”的派生事实。

推荐消费最近 5 个有效交易日时生成时序摘要：

- `first_seen_date/last_seen_date/seen_days_5d/consecutive_days`；
- `best_rank/current_rank/rank_change/score_change`；
- `profiles/sources` 的新增与消失；
- 首次出现至今价格变化、当前是否仍过硬门；
- 最近 7 日有界新闻标题/来源/时间/情绪和窗口完整性。

历史候选只能提供“持续性与变化”特征；进入本次 LLM 名单前必须用当前有效行情和当前因子重算，不得把三天前的高分直接当今天的买点。

### 4.3 第三批：`candidate_miss_audits`

每日收盘后针对昨日信号日生成两组审计：

- **missed_leader**：今日机会集中表现靠前、昨日未被最终选中的标的；
- **false_positive**：昨日被选中/给 buy，但今日明显落后或触发严重不利波动的标的。

每行固定昨日漏斗：

`absent -> filtered -> pool_full -> scored -> llm_list -> picked/watch/buy`，并保存昨日的排除原因、排名、来源、LLM 是否看到、最终动作、今日结果标签及可交易性。

确定性原因优先：没进发现池、用户偏好过滤、流动性/涨停不可买、评分名次不足、通道名额、去相关、行情过期、LLM 拒绝、风险门控。LLM 只能在事实完整后生成可选摘要，不能替代漏斗归因，也不能直接改分。

## 5. 风险等级与提醒策略

### 5.1 程序信号分层

第一版参数必须集中、版本化并落评估快照，禁止散落魔法数字。建议语义如下：

- **硬风险**：用户明确计划止损被有效行情触达；持仓逻辑卡明确失效且已到复核点；多项结构风险共振。
- **动态保护**：持仓峰值回撤、ATR 波动止损线、盈利回撤后跌破短中期趋势。单看“涨了多少”不自动要求卖出。
- **趋势破坏**：刚跌破 MA20/MA60、短中期均线转弱、放量下跌；长期在均线下不每天重复报。
- **事件风险**：业绩变脸、大比例解禁、龙虎榜明显净卖等既有 `SellReview`；除权只提示账面口径变化，不凭除权本身升级为清仓复核。
- **数据质量**：行情 stale 时为 `unknown`；日线不足或关键事件读取失败时为 `partial`，技术/缺失来源不参与判断。若没有任何可独立确认的风险事实，结论仍为 `unknown`；若 fresh 行情已明确触发计划止损等硬事实，则保留对应等级并同时展示缺口。禁止把 incomplete 降为 normal。

聚合原则：单一弱信号通常为 `watch`，强信号或两个独立中等信号为 `review`，明确计划止损触达或强风险共振为 `urgent`。任何分级都附具体事实和失效/恢复条件，不输出裸分数。

第一版确定性映射至少锁定以下边界：

| 事实 | 单独命中 | 与独立风险共振 |
|---|---|---|
| 明确计划止损被 fresh 行情触达 | `urgent` | 保持 `urgent` |
| 明确计划止盈触达 / `cost_gain` | `watch`，提示复核落袋，不自动判卖 | 趋势破坏时升 `review` |
| 用户配置的 `cost_drawdown/peak_drawdown` 命中 | `review` | 强结构破坏时升 `urgent` |
| MA20 刚跌破 | `watch` | 与 ATR/事件风险共振时升 `review` |
| MA60 刚跌破或 ATR14 动态保护线被首次有效跌破 | `review` | 两者同时或叠加高风险事件时升 `urgent` |
| `SellReview` high / med | `review` / `watch` | 与 MA/ATR/亏损风险共振时最多升一级 |
| 除权口径事件 | 仅提示口径，不单独形成卖出等级 | 只由其他独立风险决定等级 |
| stale/无 fresh 行情 | `unknown` | 不得与其他事实凑成风险共振 |
| 样本不足/关键查询失败 | 无独立事实时 `unknown` + `partial`；已有独立硬事实时保留其等级 + `partial` | 缺失项不得充当风险证据或凑共振 |

ATR 只使用本地、截至评估时点已完成的日线计算 ATR14；动态保护线参数按短线/长线与风险偏好集中映射并写入 `assessment_version` 参数快照。盘中判断使用上一已完成交易日算出的保护线和 fresh 现价，盘后再用完整日线确认；不得把盘中未完成 K 线混入日线 ATR/MA。

### 5.2 AI 的位置

- 第一批保留现有 `PositionAdviceService`，改为可从 `review/urgent` 卡片按 `position_id` 精确发起，只分析这一笔并注入最新聚合评估。既有手动“分析全部持仓”可兼容保留，但不是自动流程，也不改变程序风险等级。
- `normal/watch/unknown` 不自动调用 AI；全量“分析所有持仓”入口可保留，但不作为后台自动策略。
- AI 不得把程序硬风险改写为“没有风险”，不得伪造未提供新闻/财务；非法枚举、空理由和证据核验失败继续 fail-closed。
- 自动盘后 AI 只作为后续可选开关，必须有每日上限、同事实哈希幂等、明确 token 成本与失败降级；首批不默认开启。

### 5.3 通知与待办

- 未持有推荐：不建主动卖点规则、不进账本待办，继续在推荐追踪页安静记录。
- `watch`：持仓页显示，默认不推送。
- `review`：进入 ledger Todo；可按用户通知总闸推送一次。
- `urgent`：高优先级 Todo；相同事实同日去重，等级从 review 升 urgent 时允许再次提醒。
- `unknown`：只在持仓页提示“数据不足，无法判断”，不进入卖出待办，不能与 urgent 文案混用；持续 unknown 复用数据缺口观测，不重复推送。
- 用户已处理/忽略的同一事实不被扫描重新拉回；新交易日、新事实、严重度升级才重新出现。

## 6. 分批实施

### 第一大批：推荐提醒止噪 + 统一持仓卖出决策闭环（P0）

目标：用户上线后立即感受到“提醒只和真实持仓有关，并且能解释为什么需要复核”。

交付范围：

1. 删除日报成功后自动调用 `createSellAlerts` 的行为；日报仍生成推荐和研究结果。
2. 启动时幂等暂停历史 `note LIKE '收盘日报 %推荐%卖点'` 且仍 active 的自动规则，保留行和历史事件用于审计；不得暂停用户手工创建的普通到价规则。
3. 新建 `PositionExitAssessment`、纯程序信号采集/聚合器和版本化参数。
4. 复用持仓计划价、成本、峰值、AlertEvent、SellReview、日线、资金/事件事实，增加 ATR/趋势组合判断；数据不足 fail-closed。
5. 把评估接入既有提醒轮/盘后链路，避免再开一个重复拉行情的高频循环；落库前重验持仓状态与用户归属。
6. Today/持仓页消费统一最新状态，显示等级、主因、证据时点、下一步；不做卡片套卡片。
7. `review/urgent` 可按单个 `position_id` 请求现有 AI 卖出建议，并把评估快照注入；普通/未知状态不主动烧 token。
8. 旧 Alert/Guard/SellReview/API 兼容，手工提醒模板仍可用；推荐追踪数据不删除。
9. 增加迁移、幂等、并发平仓、用户隔离、stale、等级转换、同日去重、旧规则精准暂停、AI 精确持仓范围和前端类型/交互测试。

验收：

- 新日报不会因推荐创建任何卖点 `AlertRule`；旧自动规则只暂停一次且用户手工规则不受影响。
- 没有真实持仓时卖出决策与 ledger Todo 均为空。
- 同一事实重复评估不刷行、不刷提醒；平仓竞态不产生孤儿评估。
- stale 行情显示 unknown，不生成 hold/trim/exit 假结论。
- 计划止损、MA 刚跌破、峰值回撤+趋势破坏、事件风险和正常持仓均有反例测试。

#### 第一大批实施记录（2026-08-10）

- **已完成止噪**：日报推荐、推荐追踪和历史事实全部保留，但新日报不再创建推荐止盈/止损 `AlertRule`；启动迁移只暂停名称严格匹配“收盘日报 YYYY-MM-DD 推荐止盈/止损卖点”、方向/阈值/一次性语义也符合旧系统生成特征的 active 规则。规则与 `AlertEvent` 不删除，重复启动幂等，普通手工到价规则不受影响。
- **已完成统一事实闭环**：新增 append-only `PositionExitAssessment`（参数版本 `pea1`），仅评估本人仍为 holding 的真实持仓，落库前在事务内重验用户、持仓状态、symbol 与 market。输入聚合计划价、成本/盈亏、峰值/回撤、AlertEvent、SellReview、MA20/MA60、ATR14 保护线、趋势和数据时点；日线严格按 fresh 行情自身交易日截断，盘中不混入观测日未完成 K 线。stale 为 unknown；样本、坏根或旁路查询不完整标 partial，不参与技术共振且不得吞掉已触发的计划止损等独立硬事实。
- **已完成消费收口**：提醒轮复用已取得的持仓行情，19:40 盘后轮复用同一行情快照；相同事实不刷库，只在等级、主因、关键阈值首次穿越或盘后快照等有意义变化时追加。持仓页、Today ledger Todo 和通知均消费同一评估事实；normal/watch 仅展示，review/urgent 按统一通知总闸去重，unknown 不进 Todo、不推送。原始 Alert/Guard/SellReview 继续保留审计和兼容状态机，但在已有统一评估后不再重复占用 Today 或直接发送卖出风险通知。
- **已完成精确 AI 复核**：`PositionAdviceRequest` 支持 `position_id`，服务端同时核验 `user_id + position_id + symbol + holding`，只给 review/urgent 卡片提供逐笔入口并注入最新评估。既有“分析全部持仓”入口继续兼容；高频评估不调用 LLM，AI 结论不能改写或降低程序风险等级，非法枚举、空理由、证据失败继续 fail-closed。版本更新为 `pa3`。
- **实际实现边界**：未新建控制器或路由，复用并扩展现有持仓列表和持仓建议接口；未新建调度循环或行情请求链路。ATR/MA 第一版采用集中、版本化的保守基线并把参数快照固化到每条评估，后续只有在真实样本支持下才按周期/风险偏好分层，不能无版本静默改阈值。
- **统一审查修复**：`GuardEvent` 自动迁移新增 `position_id` 并把通知唯一键升级为 `(user_id, position_id, symbol, kind, trade_date)`；普通守护事件固定为 0，原有去重不变，同一股票的不同成本持仓可分别通知。评估按行情实际交易日分组补峰值和截取日线，避免周末/休市日发生 as-of 偏移。
- **程序化验证**：定向后端测试覆盖旧规则精准暂停、矩阵与共振、unknown、迁移/隔离/平仓竞态/幂等、Todo 状态及逐笔 AI 范围；`powershell -ExecutionPolicy Bypass -File scripts/verify.ps1 -Mode full` 已通过全部 Go 测试与前端生产构建。浏览器用真实 CSS viewport 目验 375×812 与 1440×1000，风险证据、时点、状态和操作区均无横向溢出或重叠；临时服务、浏览器和数据已清理。
- **提交信息**：`推荐提醒止噪与统一持仓卖出决策`；提交哈希以本批完成后的 `git log` 为准。

### 第二大批：全市场日更发现 + 近 5 日候选记忆 + 推荐接线（P1）

目标：推荐不再只依赖请求当刻的几个榜单，能看到全市场候选的持续增强与当前买点。

交付范围：

1. 新建 DiscoveryRun/Item，挂在因子快照成功发布后，全局幂等运行；支持启动补跑、partial/failed 和状态查看。
2. 复用内置条件树/宽表建立多通道 Top-N，不逐用户扫描、不调用 LLM。
3. 推荐建池新增 `daily_discovery` 与 `recent_discovery` 来源，保留现有 watchlist/榜单/strategy_signal 作为实时补充和降级路径。
4. 最近 5 个交易日候选必须重新过当前行情、流动性、涨停、黑名单和用户 RecFilters；旧分不直接沿用。
5. 多通道采用固定、可审计的名额与稳定排序，避免一个总分把回踩/价值通道挤没；先记录来源事实，不在本批手调量化权重。
6. LLM 输入增加紧凑时序摘要与最多若干条真实新闻 brief；总 token 预算、候选集合和越池校验不放松。
7. 设置页明确“当前自动发现范围：A 股全市场”，复用已有价格/市值/换手/板块/黑名单/风险周期偏好，不造港美股配置。
8. 管理页或推荐页展示发现日期、覆盖数、通道、首次出现、连续天数和排名变化；局部失败不冒充空池。

验收：

- 5500 只规模只发生一次系统扫描，两个用户生成推荐不触发两次全市场扫描。
- 重启/重复挂点同日不重复写；部分宽表或过期因子不生成“成功完整”工件。
- 历史候选在当前已不合格时不能进 LLM；新来源在 CandidateEvent 和召回评估中可归因。
- LLM 看到的是时序摘要和真实有界新闻，不是全量 K 线/新闻正文。

### 第三大批：每日漏选/误选复盘 + 候选召回诊断（P1）

目标：每天都能回答“今天强的票昨天为什么没看到”和“昨天看中的票为什么错了”。

交付范围：

1. 新建每日审计事实和幂等盘后任务，基于相邻有效交易日，不拿周末/停机日补造比较。
2. 用昨日 CandidateDiscoveryItem、RecommendationCandidateEvent、用户筛选、LLM 输出和昨日 as-of 新闻重建漏斗。
3. 同时产出 missed leader 与 false positive，机会集排除停牌、次日不可买和流动性不足标的。
4. 将 `absent/filtered/pool_full/scored/llm_list/picked` 细化为用户可读原因，并能下钻昨日事实。
5. 在推荐评估页增加每日复盘、来源/通道漏选率、LLM 拒选后表现、量化 Top-N 与 AI 的成对结果。
6. 可选 LLM 只对确定性事实做摘要，关闭/失败时完整报表仍可用；摘要不写回权重。
7. 增加最小样本、版本分层和样本不足声明，禁止用一两天结果宣称推荐变准。

验收：

- 修改今天数据不能改变昨日输入事实，只能改变今日结果标签。
- 一字涨停买不到的今日龙头不记为昨日可执行漏选。
- 每条漏选与误选能落到唯一漏斗原因；缺事实明确 unknown，不事后猜测。
- 报表同时展示漏选和误选，不能只给“本来能赚多少”的幸存者叙事。

### 第四批：证据驱动的排序与 AI 角色调整（P2，受样本门槛约束）

启动条件：第二、三批已在线积累足够有效交易日，且 S3-6C score-blind/selection outcome 有成熟 matched-K 批次。

可能动作按证据选择，而非预先承诺全部实施：

- 若 pool Recall 低：增加有效发现通道或调整通道名额，先解决召回；
- 若 Quant Top-N 稳定优于 AI：AI 降为解释/风险否决，不再主导选股；
- 若 score-blind 优于带分输入：生产 prompt 减少量化分/排名锚点；
- 若 AI 在特定市场状态或票型有增量：只在该分层启用，不全局放权；
- 若手工分排序弱且历史 PIT 样本达标：按 `RECOMMENDATION_ACCURACY_PLAN.md` S4 先上线线性/Logistic baseline 的影子结果，再考虑 LightGBM；
- 新排序必须走 walk-forward、成本、严重亏损率、覆盖率和 champion/challenger 发布门，不能直接替换生产。

## 7. 文件影响与并行边界

- 第一批：`model/{alert,sellreview,position,...}.go`、`service/{dailyreport,alert,guard,sellreview,positionadvice,todo,...}.go`、controller/router、`Positions.vue`、Today/API 类型与对应测试。

## 8. 每批通用工程要求

1. 先读本规划、`ROADMAP.md` 相关防回归条目和直接涉及的旧规划章节，再读代码；不要按旧文档行号盲改。
2. 新表/新列必须加入 `AllModels()` 并由启动 `AutoMigrate` 自动完成；只有 AutoMigrate 无法表达的数据迁移才写幂等启动迁移，用户不手工执行 SQL。
3. 所有用户事实按 `user_id` 隔离；系统级发现使用明确 system/global 语义，不用 `user_id=0` 伪装。
4. 定时任务要有幂等、重入锁、截止时间、部分失败、启动补跑和安全日志；不得无界 goroutine 或逐用户全市场 I/O。
5. 任何涉及历史判断的查询都带明确 `as_of`，未来数据、旧新闻和当前重算值不能污染历史事实。
6. 纯程序函数表驱动测试，数据库覆盖幂等/并发/隔离/迁移，前端通过类型检查与生产构建；响应式改动检查 375px 与 1440px。
7. 开发中优先跑定向测试；收尾执行 `scripts/verify.ps1 -Mode full`。全量失败必须区分本批回归与既有顺序依赖，不得为了变绿删测试或放宽业务约束。
8. 每批完成同步更新本文实施状态与 `ROADMAP.md`；若改变已有业务边界，再更新对应旧规划。
9. 不修改个人使用的 `编译推送步骤.md`，不启动长期前后台开发服务，除非当前任务确实需要浏览器目验；启动后必须在结束前停止。
10. 每批完成后提交代码但不要 push，等待统一审查、补修与推送。
